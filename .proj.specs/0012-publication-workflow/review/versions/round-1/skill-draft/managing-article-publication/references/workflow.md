# Workflow contract

Apply only the repository's approved version of epic 0012. This draft is not that approval.
Use real CLI help/API capabilities; the proposed v2/automation interfaces are not implemented
by this document. Existing v1 local behavior remains in local.md, including ancestry refusals.

## Shared engineering baseline

Inspect current main/staging and outstanding PR states. Record full commits and every changed
path's mode/hash, including deletions. Classify common engineering, management/history,
published content, unapproved articles **and revisions**, exclusive assets and target-role
configuration. Resolve ownership/shared-content ambiguity before preparation. Do not assume
an open prerequisite PR has landed.

Prepare only individually approved common engineering/management for main. Keep pending
article bodies, revisions, listings and assets out. Then prepare main-to-staging integration
and prove remaining candidate bytes, images, metadata and URLs are preserved. Conflicts need
reviewed patches, never blanket ours/theirs or a copied staging tree. Immutable fixtures and
old assertions stay unchanged; new current behavior needs an explicit reviewed successor.

## Article sources and shared preview

Start sources from pinned main. Integrate clean topics into staging with explicit merge
commits; author feedback goes back to the source topic. Do not merge staging into a source
or rewrite a topic already integrated. A topic reachable from staging is not automatically
contaminated in v2; its history must still pass the approved admission policy.

V2 requires owner-reviewed M0/registry policy accounting for every candidate/revision, assets
and exact dependencies. Examine all non-main commits and shared-content patches. Reject
staging integration ancestry, other candidate history even after revert, unknown commits,
incomplete history and omitted ownership. Only approved main refresh merges are permitted.
Legacy contaminated sources need an explicit reviewed old-to-new provenance record and owner
approval. Reconstructing files on a new branch does not prove the old history was clean.

For shared preview, observe the existing alias and deployed commit reviewed by the author.
Do not change deployment settings or create per-article deployments as part of this workflow.
Without actual served identity, report preview evidence missing; a branch tip is insufficient.

## Main-to-staging sync

Read current refs, not event payload alone. Main already contained in staging means no-op.
Otherwise compute an independent merge in disposable storage, validate staging role, and
preserve every pending candidate. Exact conflict/check failures stop without target mutation.

Use the designated permanent ticket-owned operational branch and at most one owned open
sync PR. Verify branch/PR identity before updates; no force push, unrelated branch reuse or
deletion. Non-force head updates must yield the independently computed result tree. If no
designated branch or approved policy exists, return a plan rather than allocate one implicitly.

Participating preview/sync/publication writers serialize in one repository group. Re-read
refs before mutation; drift restarts preparation. Read back ambiguous API outcomes before
retry, with at most three retries per run. Report exhausted retries rather than duplicate PRs.
Initial automation opens/updates PRs only. Merge needs independent applicable authority.

Do not assume bot push/PR events execute checks. Require the trusted validation dispatch's
actual successful run bound to base/head/tree/policy. Writer credentials cannot enter the
candidate/build process. Repository permission/protection/latest-base checks need an expressly
authorized remote exercise before activation; local API stubs prove only local behavior.

## One selected publication

Bind approval to one article identity/revision, main/source/dependency commits, complete
registry/policy, reconstructed tree and the actual preview deployment reviewed. Rebuild from
current main plus that article and exact reviewed dependencies; never promote all of staging.
Shared listing/config paths need content review, not folder/path permission alone. Exclude
every unselected body/revision, route, listing/search/RSS entry and exclusive public asset.

Independently verify complete source modes/hashes/diff, then use the existing reviewed
toolchain under an enforced no-network build boundary. Missing isolation/runtime stays
blocked. Record the actual build separately from output scanning; signatures are only
supplementary, and missing signatures mean exclusion-unverified. Preserve permitted immutable
baseline aliases as data; reject new links, submodules and escaping/executable includes.

Drift of source/main/dependencies/policy/tree or reviewed deployment binding expires approval
and readiness. Complete preparation and review before requesting any missing final authority.
Use project message skills for authorized commits/PRs; a PR request alone does not allow merge.
Verify protections/latest-base checks before operational use; a head-only API guard does not
lock the base. Check actual landing tree when authorized landing occurs; mismatch is an
incident. Main landing and served production are separately observed states.

After landing, sync back without removing the article or other candidates; retire only the
landed unapproved revision from the next reviewed registry. New revisions remain candidates.
Use the future-action reference for reviewed revert and fresh re-publication authority.
Ticket done still requires actual authorized staging ancestry and all ticket acceptance
criteria under ADR-0006. PR-ready, main-only landing and preview-only integration cannot
substitute for that evidence. Do not change existing ticket states during planning.

## Packaging and installation

The final approved skill extends the existing fourth product package. Edit its canonical
source once and use the existing materializer for both runtimes; do not edit generated copies,
add a fifth root or tune the other three writing packages. Preserve invocation policy and
historical package evidence through an exact reviewed successor. No installation, activation,
Actions changes, Cloudflare changes or external mutation is implied by this draft.
