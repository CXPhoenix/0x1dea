## 建議拆成四張

每張都交付可以單獨展示的完整行為，包含必要指引、套件整合與驗證；沒有另開只寫文件、只產生套件或最後才補測試的水平分層票。

| 順序／提案 | 交付內容 | 真正的前置票 | 可展示的結果 | 完整交付與測試表 |
|---|---|---|---|---|
| 1／A | 本機筆記與 current source guard 相容 | 無 | 有效 main／staging 案例在筆記保存前、保存後、更新後都通過；不合法物件與來源碰撞仍拒絕 | [A：6 列計畫](A-local-notes-current-guard.md) |
| 2／B | 可自由聊、直接試寫的 article-discovery 入口 | 無 | 用 Codex／Claude 從片段或心情開始；不知道目的、受眾也能寫，只聽就不擅自改稿 | [B：11 列計畫](B-free-conversation-entry.md) |
| 3／C | 按需保存／續寫、建立或沿用詞彙檔 | A、B | 要求保存才整理；返回時保留暫定與確認狀態；單一舊詞彙檔直接沿用 | [C：11 列計畫](C-optional-context-glossary.md) |
| 4／D | 按需公開檢查與既有文章交付路由 | B | 指出具體段落／素材的已知結果或缺口；建立文章、改稿、預覽仍走既有負責流程 | [D：8 列計畫](D-public-preparation-routing.md) |

依賴邊只有 **A → C、B → C、B → D**。A 驗證工程來源與本機產物的邊界，不需要先有 skill；B 的完整聊天路徑不寫筆記，所以不需要 A；D 可直接檢查提供的文章與素材，不要求先保存或建立詞彙表，所以不依賴 C。

建議實作順序 **A → B → C → D**，方便同一位作者維護共用 canonical 指引與有限來源身分。這是減少編輯衝突的排程建議，不增加假的阻擋關係。若日後平行實作，須遵守各票分支／獨立 worktree、單一寫入者及有限來源紀錄整合規則。

每票完成時只宣告該交付路徑的結果。B 先交付完整的自由聊路徑，C、D 再加入各自可用的條件分支；不提前放上不存在的參照、宣稱未完成能力可用，或把尚未完成的 epic 報成已驗收。

## 不改變的寫作原則

- **先自由聊，有需要才整理。** 目的、受眾、論點與文類都可以未知或刻意不設定；想開始寫就開始。
- 問題必須影響下一步、文意或重要事實；可查的事實由 agent 查，已回答的作者選擇直接沿用。深入訪談保留給明確要求。
- 只聽、不改稿、保留某句話、維持立場或留白，都屬有效要求；不添加個人經歷、心理定論或和解結尾。
- 純寫作不需要工程 spec／ticket／測試表。skill、CLI、renderer、設定與網站行為修改仍走工程流程；這四張票都屬工程維護。
- 保存須來自要求或既有有效授權；一般聊天與單純文章檔案要求不額外建立 PROJECT／GLOSSARY。
- GLOSSARY 預設需要「啟用保存＋至少一個已解決且需重用的術語＋沒有現行相容詞彙檔」。明確要求空白骨架則照辦，不編造詞條。
- 單一 GLOSSARY 或文章舊 CONTEXT 直接沿用；兩份未指定權威或指定無效時，只暫停詞彙寫入，其他文章繼續。工程 CONTEXT 保留工程用途。
- 公開檢查在要求準備公開時才啟動；未觸發類別不加問卷，已知缺口不冒充通過，討論完成不等於發布。

## 測試計畫怎麼讀

四份提案各有專案要求的五欄表：`Seam | Test intent | Scope | Acceptance criterion | Boundary conditions`，另以 A01–D08 標示可追溯列號。**36 列是計畫列，不是已執行測試數，也不等於固定測試數；一列可能涵蓋數個明列的輸入變體。** 下方另列 3 列跨票驗證。測試與評估都尚未撰寫／執行。

| 提案 | 測試重點 | 特別防止的退步 |
|---|---|---|
| A | native verifier 的正常生命週期、形狀拒絕、HEAD／index／受信任清單碰撞、精確來源與歷史保留 | 把整個資料夾放行；只測私有 helper；用本來就失敗的案例宣稱筆記驗證成功 |
| B | 實際技能路由、片段起稿、只聽、改方向、受保護表達、問題必要性、工程分工、實體套件產生 | 起手就問目的／受眾；重開訪談；以檔案存在推論 host 已執行 |
| C | 對話→保存→返回、失敗讀回、穩定 key、詞彙建立條件、舊檔權威、來源文字與寫入權限、guard 交集 | 暫定變確認；沒術語也建空檔；重問唯一詞彙檔權威；為了通過 guard 擅自搬／刪自訂筆記 |
| D | 文章 CLI／改稿／預覽路由、四類公開檢查的具體結果、未觸發與未解情境 | 把公開檢查塞進起稿；只提醒卻算完成；已答公開範圍重問；把引用當授權或把缺口當發布就緒 |

行為評估使用固定情境輸入、實際回應、動作紀錄及明確判準。判定的是「採取了哪些行動、保留了哪些作者選擇、留下哪些檔案」，不要求相同句子、固定問題數或文風分數。歷史 E1–E8 的輸入、判準與結果維持原樣，新情境另記。

若實作觸及 lint 管理的程式，跑 `pnpm lint`；若觸及會影響網站產出的行為，才加受影響的 build／真實 browser 驗證。本 epic 不預定修改 renderer 或文章內容，也不以網站 build 代替對話、檔案或 native CLI 驗證。不安裝工具，不改帳號／trust／credential；既有工具不可用時如實保留缺口。

每票仍須依工程流程留下 coverage report table，接續 code review、security review 與對應實際表面的驗證。沒有量測的覆蓋率寫「未量測」，不將這些計畫列換算成百分比。沒有實際 host 證據的部分不可宣告該 runtime 的行為驗收完成；也不將本次確認解讀成新的 commit／push／PR／merge／deploy 授權。
